# STUDIO 项目级同步架构方案（Phase 2）

日期：2026-05-08
状态：待确认
范围：项目跟随账号同步、项目图片转图床、冲突处理、同步门禁

---

## 1. 页面目标

在“账号资产同步”已经覆盖用户偏好与敏感配置的基础上，补齐“项目级同步”能力，让用户可以：

1. 继续保留本地项目工作流，不破坏现有使用习惯。
2. 在图床已正确配置时，将项目安全地提升为“可跨设备同步”的状态。
3. 对整个项目执行一次性“本地引用 → 可公开访问图床链接”的迁移。
4. 在多端使用时，避免空项目、旧项目、未转图床项目覆盖有效数据。

---

## 2. 用户主任务

### 主任务 A：判断当前项目能否同步
用户需要快速知道当前项目是否：
- 仍含本地图片引用
- 已满足同步前置条件
- 存在远端版本
- 存在冲突风险

### 主任务 B：把项目切换为可同步状态
用户需要在不破坏原项目结构的前提下：
- 开启图床
- 填写有效 key
- 手动执行整项目转图床
- 获得明确的转换结果与失败项

### 主任务 C：将项目同步到账号并在其他设备恢复
用户需要：
- 主动同步当前项目或选定项目
- 在另一台设备拉取相同项目
- 遇到冲突时看到明确决策，而不是静默覆盖

---

## 3. 设计原则

1. 本地优先：项目仍然首先保存在本地 IndexedDB。
2. 手动升级：只有用户明确执行“转图床”后，项目才进入可同步状态。
3. 明确门禁：未配置图床、图床无效、仍含本地引用时，不允许项目云同步。
4. 非破坏性：保留现有本地图片引用工作流；未开启图床时上传/生图继续使用原本本地形式。
5. 项目级冲突隔离：冲突按“单项目”处理，不影响整个账号的其他项目。
6. 先元数据后完整快照：先同步项目索引，再同步完整项目快照，便于列表、状态与审计。

## 4. 信息架构

### 一级入口
放在工作区内，而不是设置首页堆叠：

1. 当前项目同步面板
2. 项目资源状态卡
3. 整项目转图床操作区
4. 项目同步历史 / 冲突提示

### 二级入口
以下内容进入二级入口或折叠区域：

1. 失败资源明细列表
2. 同步审计日志
3. 远端历史快照版本

这样可以保证首页只聚焦“当前项目是否能同步、为何不能同步、下一步该做什么”。

## 6. 项目可同步门禁

只有同时满足以下条件，项目才允许进入云同步：

1. 图床已启用，且不是 `none`
2. 当前图床配置已通过基本校验
3. 项目内不存在 `blob:` / `data:` / `jk-topic-asset://` / `xc-topic-asset://` / `ATTACHMENT_` 等本地引用
4. 项目快照已通过存储清洗

### 门禁输出状态

#### 状态 1：未启用图床
文案：当前项目仅本地可用，启用图床后才可同步
操作：引导去配置图床

#### 状态 2：图床已启用但仍有本地引用
文案：需要先执行“整项目转图床”
操作：显示风险数量、展示转换按钮

#### 状态 3：图床可用且无本地引用
文案：当前项目可同步
操作：显示“同步到账号”按钮

#### 状态 4：远端版本更新
文案：该项目在其他设备已更新
操作：进入冲突决策

## 7. 资源策略

### 7.1 保留旧行为
当图床未开启时：
- 上传图片继续保留本地形式
- 生图结果继续保留本地形式
- 不强制迁移
- 不允许该项目同步到账号

### 7.2 开启图床后的新行为
当图床开启且有效时：
- 新上传图片默认走图床上传
- 新生成图片默认转为图床链接
- 新项目逐步天然满足同步条件

### 7.3 整项目转图床
这是项目升级为可同步状态的关键动作。

转换流程：
1. 扫描项目中的所有图片引用
2. 识别本地引用
3. 逐个读取资源内容
4. 上传至当前图床
5. 回写项目中的对应 URL
6. 记录成功数、失败数、失败原因
7. 转换完成后自动重新评估项目同步门禁

失败处理：
- 部分失败时不允许同步
- 必须清楚列出失败资源
- 用户可再次重试失败项或重新执行整项目转换

## 8. 冲突模型

冲突不再按“整个账号资产”处理，而是按“单项目”处理。

### 比较基准
每个项目都维护：
- local.updatedAt
- remote.updatedAt
- remoteRevision
- lastKnownRemoteRevision

### 判定规则

#### 情况 A：远端不存在
直接上传本地项目

#### 情况 B：远端存在，且本地记录的 `lastKnownRemoteRevision` 与远端一致
允许上传，形成新 revision

#### 情况 C：远端存在，且远端 revision 已变化
说明其他设备已更新，进入冲突态

### 冲突决策

1. 以远端为准
   - 拉取远端覆盖本地项目
2. 以本地为准
   - 在用户确认后强制生成新 revision 覆盖远端
3. 另存为副本
   - 将本地版本复制为新项目，再上传为新的 project_id

默认推荐：
- 普通用户优先看到“恢复远端”与“本地另存为副本”
- “强制覆盖远端”放二级入口，避免误操作

## 11. 同步流程

### 本地 → 云端
1. 读取当前项目
2. 扫描本地资源风险
3. 校验图床状态
4. 若不满足门禁，阻止同步并给出原因
5. 生成存储快照
6. 拉取远端摘要
7. 比较 revision
8. 无冲突则写入快照与索引
9. 更新本地 lastKnownRemoteRevision

### 云端 → 本地
1. 获取项目列表或指定项目
2. 拉取远端快照
3. 恢复到本地 IndexedDB
4. 更新本地 store
5. 标记来源 revision

## 13. 风险点

1. 本地资源无法重新读取
   - 例如历史 `blob:` 已失效
   - 需要在转换前就给出失败提示

2. 大项目转换耗时长
   - 需要进度条与可中断体验

3. 图床限流 / 失败
   - 需要失败重试与批量节流

4. 跨设备并发修改
   - 必须严格依赖 revision 比较，不可静默覆盖

5. URL 替换不完整
   - 需要覆盖项目对象中的所有图片引用位置

### Phase 2C：项目列表与多端管理
目标：支持账号下项目列表、跨端选择恢复

包括：
- 账号项目列表

## 16. 本阶段结论

建议采用：
- 本地项目保留
- 图床作为项目同步前置条件
- 手动整项目转图床作为升级动作
- 单项目 revision 冲突控制
- 索引表 + 快照表双层存储

这样可以最大程度避免：
- 空项目覆盖有效项目
- 未转图床项目跨端失真
- 本地引用在其他设备无法恢复
- 首页堆过多低频同步设置
