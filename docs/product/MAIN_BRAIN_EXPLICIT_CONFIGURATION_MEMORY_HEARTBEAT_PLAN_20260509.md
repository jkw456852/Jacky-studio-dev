# 主脑显性配置 / 长期记忆 / 心跳机制产品方案

日期：2026-05-09  
状态：待实施方案  
范围：主脑配置中心、Soul / User / Workflow / Memory / Heartbeat / Bootstrap、与现有主脑运行时及角色治理体系整合

---

## 1. 背景

当前项目里的主脑已经具备较强的运行时能力：

- 能做多轮规划与执行
- 能自主调用工具并根据失败结果重规划
- 已接入联网搜索与研究态链路
- 已具备角色治理、角色版本、审计与回滚基础
- 已具备一定的全局偏好注入与运行时状态感知

但从“产品级主脑”角度看，仍有几个明显短板：

1. **主脑长期配置是隐式的**
   - 当前规则分散在共享提示词、用户长期偏好、角色层和运行时 metadata 中
   - 用户无法直观看到“主脑长期依据什么在工作”

2. **长期记忆缺少显性产品入口**
   - 现在更偏向“会话上下文 + 运行态拼装”
   - 用户缺少“它记住了什么 / 为什么记住 / 如何修正”的明确入口

3. **缺少周期性整理机制**
   - 主脑主要在用户触发时工作
   - 缺少定期压缩、偏好提炼、角色老化检查、失败总结这类低频后台任务

4. **缺少初始化引导**
   - 新用户第一次使用时，主脑能力很强，但调教门槛高
   - 缺少一套 onboarding 帮用户快速建立主脑风格、工作方式与默认边界

5. **强在运行时，弱在可感知性**
   - 我们在自治执行、工具闭环、角色治理上已经强于很多纯配置型方案
   - 但在“可见、可配、可养成、可解释”上仍有明显提升空间

---

## 2. 产品目标

构建一套**不退回纯 Markdown 配置**、但具备类似显性配置体验的主脑体系，使主脑同时具备：

1. **可见性**：用户知道主脑的长期设定、工作方式、记忆来源
2. **可编辑性**：用户可以直接编辑主脑风格、用户画像、工作流和周期任务
3. **可审计性**：配置变更、记忆提升、角色治理、回滚都有记录
4. **可养成性**：主脑会随着用户偏好与历史行为逐步更像“专属搭档”
5. **可执行性**：保留当前 runtime + tool loop 优势，不牺牲自治能力

## 3. 核心原则

### 3.1 不回退成“纯文件驱动智能体”
借鉴外部方案的信息架构，但底层仍坚持：

- typed asset
- 结构化同步
- 版本与审计
- 运行时状态机
- 角色治理
- 统一 UI 产品入口

### 3.2 输入区不继续膨胀
输入区只保留：

- 当前主脑状态摘要
- 快速入口
- 当前会话角色 / 模式切换
- 当前会话级提示

复杂配置全部进入独立主脑配置中心。

### 3.3 配置层与执行层分离
- **配置层**：定义长期稳定规则
- **执行层**：根据当前任务、角色、上下文、失败结果动态决策

### 3.4 记忆必须可控
所有长期记忆都必须支持：

- 来源查看
- 人工确认
- 删除 / 降级
- 提升为长期规则
- 审计记录

### 3.5 周期任务必须克制
Heartbeat 不能演变成持续高成本后台 agent。

- 默认低频
- 有任务上限
- 必须可停用
- 每次执行必须有结果摘要
- 不允许无上限自循环

## 5. 第 1 步：产品经理

### 5.1 页面目标

构建“主脑配置中心”，让用户能够：

1. 配置主脑风格与人格
2. 维护自己的用户画像与长期偏好
3. 管理主脑工作流和执行策略
4. 查看、确认、清理长期记忆
5. 配置周期性 Heartbeat 任务
6. 完成首次初始化与后续校准
7. 把主脑配置与角色治理系统联动起来

### 5.2 用户主任务

1. 让主脑更像我想要的工作搭档
2. 让主脑理解我的偏好、目标和表达习惯
3. 让主脑记住长期有效的信息
4. 让主脑定期帮我做低频维护类工作
5. 控制主脑在角色治理中的默认权限和边界
6. 回看主脑最近为什么会那样做

## 6. 第 2 步：UI 设计师

### 6.1 页面区块划分

#### A. 主脑总览页
1. 顶部标题区
   - 页面标题
   - 当前状态说明
   - 主操作：初始化 / 最近变更

2. 配置摘要卡片区
   - Soul 摘要卡
   - User 摘要卡
   - Workflow 摘要卡
   - Role Governance 摘要卡

3. 运行状态区
   - 最近记忆
   - 最近 Heartbeat
   - 最近主脑治理动作

4. 风险与待办区
   - 待确认记忆
   - 失败心跳
   - 配置冲突提醒

#### B. 详情页共用布局
- 左侧导航
- 中间主编辑区
- 右侧说明 / 预览 / 最近变更区

### 6.2 模块布局建议

- 延续现有角色管理面板的克制产品风格
- 用卡片分区而不是整页连续表单
- 一屏只突出一个主要任务
- 右侧只承担说明、影响范围、预览，不堆复杂操作

### 6.3 低保真线框说明

#### 主脑总览
- 顶部：标题 + 说明 + 主按钮
- 中部：2x2 摘要卡片
- 下部左：最近记忆 / 最近 Heartbeat
- 下部右：风险提醒 / 待处理事项

#### Soul / User / Workflow
- 左：编辑表单
- 右：预览当前注入摘要 + 最近变更

#### Memory
- 左：记忆列表
- 右：详情 / 来源 / 操作

#### Heartbeat
- 左：任务列表
- 右：任务详情 / 下次执行 / 最近结果

### 6.4 视觉规范建议

- 页面标题：20-24 / semibold
- 区块标题：16-18 / semibold
- 正文：14-16 / regular
- 辅助：12-14 / regular
- 统一圆角：12
- 卡片内边距：16 或 24
- 模块间距：24
- 按钮高度统一
- 仅对风险 / 待确认 / 回滚做低饱和强调色

### 6.5 风险点

1. 配置项太多，容易做成后台表单堆砌
2. Memory 容易信息爆炸
3. Heartbeat 容易让用户误以为是持续高频后台 agent
4. Soul / User / Workflow 容易语义重叠，需要严格定义边界
5. 若所有说明都堆在首页，会丧失主次关系

5. 尽量复用现有主脑偏好存储入口，不平地起新烟囱

### 7.3 注入链路设计

主脑最终提示词建议拆成 6 层：

1. 系统基础层
2. 主脑 Soul 层
3. 主脑 User 层
4. 主脑 Workflow 层
5. 当前项目 / 工作区上下文层
6. 当前会话运行时状态层

角色执行时，再叠加：

7. 角色实体层
8. 临时任务覆盖层

### 7.4 Memory 工作流

#### A. 记忆候选产生
来源：
- 对话中的稳定偏好
- 用户明确说明的长期规则
- 任务后总结
- Heartbeat 自动提炼

#### B. 记忆候选分类
- 长期偏好
- 工作背景
- 审美偏好
- 禁忌与边界
- 高价值项目事实
- 可忽略临时噪音

#### C. 记忆候选去向
- 进入待确认区
- 提升为长期记忆
- 提升为 Workflow 规则
- 提升为 Role Governance 默认规则
- 丢弃

### 7.5 Heartbeat 工作流

#### 默认允许的低频任务
- 压缩最近高频重复偏好
- 汇总最近失败原因
- 提醒用户确认待提升记忆
- 检查长期角色是否长期未使用
- 检查主脑默认规则是否互相冲突

#### 禁止 Heartbeat 做的事
- 无限制联网搜索
- 无限制角色修改
- 无用户确认的高风险发布
- 无边界更新长期关键资产

### 7.6 Bootstrap 工作流

首次初始化问卷建议包含：
- 你希望主脑更像顾问、执行助手还是研究搭档？
- 你更偏好先给结论还是先展开分析？
- 是否默认优先联网搜索？
- 是否允许主脑自动生成长期角色草案？
- 是否允许 Heartbeat 定期整理长期记忆？
- 你常见的项目类型是什么？

输出：
- 初始 Soul
- 初始 User
- 初始 Workflow
- 初始 Role Governance 默认值

## 8. 第 4 步：与现有角色治理体系整合

### 8.1 要整合的原因

当前已经在做产品级角色管理。如果主脑新配置体系与角色治理割裂，会出现：

- 主脑一套长期偏好
- 角色治理另一套默认值
- 运行时再拼一套临时判断

最终导致行为不一致。

### 8.2 必须打通的点

#### A. Workflow → Role Governance
Workflow 中应包含默认项：
- 是否允许主脑自动生成角色草案
- 是否允许主脑自动升级长期角色
- 是否默认要求人工确认
- 是否允许主脑自动归档低活跃角色

#### B. Memory → Role Governance
某些长期记忆可提升为角色治理偏好，例如：
- 默认不要自动改动已稳定角色
- 新角色先以草案形式出现
- 设计类任务优先保守，开发类任务允许积极重构

#### C. Audit 融合展示
主脑配置变更、记忆提升、角色治理动作要能在产品上相互关联查看。

## 11. 第 7 步：验收标准

以下任一问题出现，视为未通过：

1. 配置入口仍然分散，看不出主脑长期规则来源
2. Memory 只是把长文本堆出来，没有确认流与删除流
3. Heartbeat 没有频率边界或风险约束
4. Bootstrap 只是空文案，没有真正产出初始配置
5. 新配置体系与角色治理默认策略不一致
6. 审计里无法追踪配置变更和记忆提升
7. UI 页面过挤、像后台 demo，而非产品级控制中心

通过标准：

- 用户能在一个入口里理解主脑长期配置
- 用户能明确看到主脑记住了什么
- 用户能控制主脑的低频自治行为
- 用户能追踪主脑长期资产的变化历史
- 新体系不削弱现有 runtime 和角色治理能力

3. 再切入主脑显性配置 / 记忆 / Heartbeat 新方向

### 12.2 新方向启动时的第一批任务
建议启动顺序：

1. 先做信息架构确认稿
2. 再做 UI 低保真
3. 再做资产模型扩展
4. 再接 runtime 注入链路
5. 再做 Memory 产品化
6. 最后接 Heartbeat

---

## 13. 结论

这套方案的目标，不是把当前主脑改造成“只有几份配置文件的轻量智能体”，而是：

**保留我们现有的运行时自治、工具闭环、角色治理、审计同步优势，同时补齐 Soul / User / Workflow / Memory / Heartbeat / Bootstrap 这套显性配置体验。**

这样做的结果是：

- 对用户来说，主脑不再是黑盒
- 对产品来说，主脑不再只是 prompt 拼装
- 对工程来说，主脑不会退回不可控的文件驱动方案
- 对后续演进来说，这会成为角色治理之上的“主脑长期操作系统”
