# 风格库与生图前编排治理优化计划

日期：2026-05-13
范围：工作台图片生成链路 / 风格库治理 / 生图前编排权限边界
状态：待实施

## 1. 页面目标
让“风格库”和“生图前编排”形成清晰的上下游关系：
- 风格库负责稳定、可复用的长期风格约束
- 生图前编排负责当前任务的临时执行规划
- 用户显式选择的风格库不再被编排器静默改写
- 4 图/多图变体默认复用一套规划，而不是被误拆成整套页面任务

## 2. 用户主任务
1. 选择一个风格库后，稳定地按该风格库出图
2. 连续生成多张变体时，复用同一套规划结果
3. 在需要时允许系统为当前任务增加临时约束，但不能偷偷改掉原风格库
4. 只有用户明确确认时，才把临时约束沉淀成新的风格库或覆盖现有风格库

## 3. 当前问题清单
### P0
1. 风格库在“跳过生图前编排”时曾经没有真正进入最终 prompt
2. 4 张变体生成被误判成 set 任务，导致每张重新规划
3. 编排器仍然存在改写当前风格库本体的能力，权限边界不清

### P1
4. `disablePlanning` 更像止血式临时开关，不是长期正确建模
5. 风格库和生图前编排同时都在管 prompt，容易冲突
6. 当前“风格库是上游约束、编排是下游执行”的产品语义没有被代码彻底落实

## 4. 功能优先级
### 高
- 锁定用户显式选择的风格库身份
- 编排器默认只读使用风格库，不改本体
- 拆分“基础风格库”和“运行时附加层”
- 多图变体复用单次规划结果

### 中
- 去掉 `disablePlanning` 作为主要治理手段
- 增加“将本轮附加层另存为风格库”的显式入口
- 在 trace / UI 中标明当前是“基础风格库 + 运行时附加层”还是“仅基础风格库”

### 低
- 对风格库治理增加更细的审计信息
- 为运行时附加层增加更可视化的差异预览

## 5. 信息架构
### A. 基础风格层 Base Style Library
由用户明确选择或保存。
负责：
- `summary`
- `referenceInterpretation`
- `planningDirectives`
- `promptBackbone`
- `promptDirectives`
- 参考图解释方式与长期风格规则

特点：
- 是资产层
- 默认只读
- 不被编排器静默覆盖

### B. 运行时附加层 Runtime Style Overlay
由当前任务的编排器按需生成。
负责：
- 当前模型适配提示
- 当前任务的构图/留白/文案密度临时约束
- 当前任务的补充执行说明

特点：
- 仅对本轮请求生效
- 不直接落库覆盖基础风格库
- 只有用户明确确认时才能提升为新风格资产

### C. 最终执行层 Final Prompt / Planned Generation
由：
- 基础风格层
- 运行时附加层
- 当前任务 prompt
- 当前参考图与一致性上下文
共同组成。

## 6. 哪些功能应进入二级入口，避免首页堆叠
以下能力不应直接塞在主生成按钮附近：
1. 将运行时附加层保存为新风格库
2. 用本轮结果更新当前风格库
3. 对比基础风格库与运行时附加层差异
4. 审计最近一次编排是否试图修改风格库

这些应进入：
- 风格库详情抽屉 / 二级菜单
- 编排结果详情面板
- 调试信息或高级入口

## 7. 治理原则
1. 用户显式选中的风格库 = 主上游约束
2. 编排器可以补充，不可以篡改
3. 本轮附加层默认临时存在，不自动持久化
4. 持久化必须由用户显式触发
5. 多图变体默认共享同一套规划，只在 prompt 上追加 variation 指令
6. 只有真正的详情页/套图/页面职责任务才进入 set 模式

## 8. 目标代码改造方案
### Phase 1：治理边界收口
目标：先让风格库不再被编排器偷偷改掉。

涉及文件：
- `pages/Workspace/controllers/useWorkspaceElementImageGeneration.ts`
- `services/vision-orchestrator/planner-model.ts`
- `services/vision-orchestrator/style-library.ts`
- `services/vision-orchestrator/types.ts`

动作：
1. 引入 Base Style Library 与 Runtime Style Overlay 的运行时拆分
2. 用户显式选择的风格库默认只读
3. 编排器输出 `styleLibrary` 时，不再直接覆盖当前基础风格库
4. 改为只生成 overlay，并在最终 prompt 组合时叠加

### Phase 2：移除临时止血开关依赖
目标：让 `disablePlanning` 退出主治理逻辑。

涉及文件：
- `services/vision-orchestrator/style-library.ts`
- `pages/Workspace/components/WorkspaceTreePromptNode.tsx`
- `pages/Workspace/controllers/useWorkspaceElementImageGeneration.ts`

动作：
1. 逐步将 `disablePlanning` 从“控制编排权限”降级为兼容字段
2. 主控制改为：全局编排开关 + 风格库只读治理规则
3. 保证即使开启编排，也不会改写基础风格库本体

### Phase 3：用户显式保存路径
目标：允许“有意识地沉淀”而不是“系统自动乱写”。

涉及文件：
- `pages/Workspace/components/WorkspaceTreePromptNode.tsx`
- `services/runtime-assets/local-user-assets.ts`
- 可能新增运行时附加层保存/应用入口相关 UI 文件

动作：
1. 提供“将本轮附加层另存为新风格库”按钮
2. 提供“覆盖更新当前风格库”按钮，并增加确认
3. 将“当前运行时附加层”与“基础风格库”做清晰区分

### Phase 4：调试与回归
目标：确保后续不再反复出现“风格库看似启用但没参与”或“多图重复规划”。

动作：
1. 在 trace 中记录 base library / runtime overlay / final prompt 来源
2. 检查单图、4 图变体、详情页 set、跳过编排、启用风格库等组合场景
3. 构建验证与手工回归

## 9. 验收标准
满足以下条件才算通过：
1. 用户选中的风格库在单图、4 图、跳过编排场景下都稳定生效
2. 4 图变体默认复用同一套规划结果
3. 编排器不会自动覆盖当前基础风格库本体
4. 运行时附加层只有在用户显式操作时才会转成风格资产
5. `disablePlanning` 不再承担主要治理职责
6. 日志和 trace 能明确区分“基础风格库”和“本轮附加层”

## 10. 实施顺序
1. 先完成基础治理方案落盘
2. 再做 Base / Overlay 结构拆分
3. 再收紧风格库持久化权限
4. 再处理显式保存入口
5. 最后统一做构建与回归
